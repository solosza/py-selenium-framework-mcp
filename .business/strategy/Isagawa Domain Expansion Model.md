# Isagawa Domain Expansion & Expert Partnership Model

**Document Type:** Internal Strategy / Operating Model  
**Audience:** Founder, Executive Team, Strategic Partners, Future Investors  
**Status:** Active – Iterative  
**Last Updated:** December 2025

---

## 1. Purpose of This Document

This document defines how **Isagawa scales across domains without scaling headcount**, equity dilution, or architectural complexity.

Isagawa’s core insight is that **technology is not the bottleneck** — **expertise is**.  
This model formalizes how domain expertise is acquired, encoded, incentivized, and governed while preserving centralized ownership of the execution engine.

This document is intentionally modular and separate from the core thesis to allow iteration without destabilizing the company narrative.

---

## 2. Core Principle

> **Isagawa does not hire expertise.  
> Isagawa encodes expertise.**

The execution engine is constant.  
The enforcement logic is proprietary.  
Only the **domain rules change**.

This enables parallel vertical expansion while maintaining a single technical and architectural backbone.

---

## 3. Why Partnerships (Not Hiring, Not Co-Founders)

Traditional scaling paths fail for Isagawa’s model:

| Approach | Why It Fails |
|--------|--------------|
| Hiring full-time domain experts | Slow, expensive, non-leveraged |
| Equity-based co-founders per vertical | Dilution, governance complexity |
| Consulting-style engagements | Non-scalable, service trap |
| Generic AI training | Loses expert-level rigor |

Instead, Isagawa uses **expert partnerships** designed specifically for **knowledge extraction, validation, and enforcement encoding** — not software development.

---

## 4. Ideal Partner Profile: Pack Contributor SME

Isagawa partners with **non-technical subject matter experts (SMEs)** as **Pack Contributors**.

### Required Characteristics
- Deep, real-world domain authority
- Clear mental model of “the correct way” work should be done
- Strong opinions backed by experience
- Willingness to externalize decision logic
- Interest in leverage, not operations

### Explicit Non-Requirements
- No software development
- No infrastructure management
- No product architecture authority
- No ownership of core IP

This profile minimizes platform risk while maximizing domain signal.

---

## 5. What Pack Contributors Provide

Pack Contributors provide **expertise artifacts**, not software.

### Pack Contribution Artifacts

| Artifact | Description | Maps to Pack Component |
|----------|-------------|------------------------|
| **Canonical workflows** | "Gold standard" processes | Enforced workflows |
| **Required steps** | Non-skippable actions | Validation checkpoints |
| **Decision criteria** | Tradeoffs and judgment calls | Rules & validation logic |
| **Escalation boundaries** | When human handoff is required | Escalation logic |
| **Approved variants** | Acceptable workflow alternatives | Variant Packs |
| **Safe variance fields** | What customers can tune | Configuration options |
| **Terminology** | Precise domain definitions | Pack metadata |
| **Ongoing validation** | Light review as domain evolves | Pack versioning |

### Transformation Pipeline

```
SME Input                    Isagawa Output
─────────────────────────────────────────────────
Workflows           ───▶     Enforced workflow steps
Required steps      ───▶     Quality gates (blocking)
Escalation rules    ───▶     Human handoff triggers
Approved variants   ───▶     Variant Packs (sell later)
Safe variance       ───▶     Config layer (sell early)
```

## 6. What Isagawa Retains (Non-Negotiable)

Isagawa retains sole ownership and control of:

- Execution engine architecture
- Enforcement logic and validation systems
- MCP tools and runtime components
- Framework code (where applicable)
- Product roadmap and prioritization
- Pricing, packaging, and distribution
- Branding and positioning
- Customer relationships and billing

Partners **license expertise**, not technology.

All derivative works remain the property of Isagawa Corp.

---

## 7. Incentive Model (Pack-Scoped Revenue)

Pack Contributors are compensated through **pack-scoped revenue participation**, not equity.

### Revenue Structure

| Revenue Stream | Ownership |
|----------------|-----------|
| **Platform license** | 100% Isagawa |
| **Pack revenue** | Shared with contributing SME(s) |
| **Custom services** | Isagawa-led, SME optional |

### Key Distinctions

- **Platform revenue** = Core enforcement runtime, gates engine, audit/traceability
- **Pack revenue** = Domain-specific workflows, rules, validation logic
- **Custom services** = Implementation, training, org-specific config

### Guiding Principles

- Compensation tied **only** to the pack(s) they contribute to
- No claim on platform revenue
- No claim on other packs' revenue
- No governance rights
- No perpetual, undefined obligations
- Incentives scale with pack adoption

Exact percentages, terms, and milestones are defined per partnership and may evolve as packs mature.

This structure:
- Aligns incentives without diluting ownership
- Protects platform valuation (100% Isagawa)
- Creates clear boundaries for SME participation
