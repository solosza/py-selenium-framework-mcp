## 3. IP Protection Rules (Hard Boundary)

### SAFE TO SELL (Info-Products)

| Category | Examples |
|----------|----------|
| Observed patterns | "10 login test scenarios most teams forget" |
| Curated examples | "Real-world page object examples from production" |
| Surface frameworks | "The 4-layer test architecture explained" |
| Templates | "Page object template (no enforcement)" |
| Checklists | "Pre-PR test review checklist" |
| Anti-patterns | "Common flaky test patterns to avoid" |

### DO NOT SELL (Engine DNA)

| Category | Why Protected |
|----------|---------------|
| The 22+ Design Decisions | Enforcement logic |
| Step ordering with failure modes | Execution sequence |
| Validation checkpoints | Gate logic |
| Pass/fail gating rules | Core IP |
| Human escalation triggers | Enforcement boundary |
| The 9/10-step tool chain | Proprietary workflow |

### The Rule

> **Never sell anything that can't fail.**
>
> If it works no matter how badly it's applied → safe to sell.
> If it requires judgment, sequencing, or validation → keep proprietary.

## 4. Tier 1: Fast Cash PDFs (3 Initial Products)

### Product 1: "10 Login Test Scenarios Most QA Teams Miss"

**Pain point:** Teams write basic login tests, miss edge cases, get burned in production.

**Contents:**
- 10 specific scenarios with examples
- Why each matters (real failure stories)
- Code snippets (examples only, no enforcement)

**Price:** $19

**Format:** PDF (Google Doc export)

**Effort:** 2-3 hours to write

**Signal tested:** Is login testing a hot pain point?

---

### Product 2: "The Page Object Naming Convention That Scales"

**Pain point:** POMs become unmaintainable chaos as codebase grows.

**Contents:**
- Naming patterns that work at scale
- Before/after examples
- Common mistakes to avoid

**Price:** $27

**Format:** PDF

**Effort:** 2-3 hours

**Signal tested:** Do teams care about POM architecture?

---

### Product 3: "Why Your AI-Generated Tests Keep Breaking (And What To Do About It)"

**Pain point:** Teams adopt AI test generation, get garbage output, waste time fixing.

**Contents:**
- Observable patterns of AI test failure
- What's missing (hint: enforcement)
- Manual workarounds (deliberately incomplete)
- Teaser: "This is what we automate"

**Price:** $29

**Format:** PDF

**Effort:** 3-4 hours

**Signal tested:** Is AI test quality a burning problem?

**Strategic value:** Direct funnel to Isagawa engine.

| X/Twitter | Hot takes, patterns | Build following |

### Post Formula (Outcome-Led)

```
[Specific result]

Here's exactly what I did:

1. [Step]
2. [Step]
3. [Step]

[Optional: Link to PDF for full breakdown]
```

**Example:**
> Reduced our flaky test rate from 23% to 4% in one sprint.
>
> Here's exactly what we changed:
>
> 1. Stopped using implicit waits entirely
> 2. Added explicit state checks before every action
> 3. Isolated test data per test run
>
> Full breakdown with code examples: [link]

## 11. IP Boundary Checklist (Pre-Publish)

Before publishing any info-product, verify:

| Check | Pass? |
|-------|-------|
| Does NOT include step ordering with failure consequences | ☐ |
| Does NOT explain why one step must precede another | ☐ |
| Does NOT include validation checkpoints | ☐ |
| Does NOT include pass/fail gate logic | ☐ |
| Does NOT reference the Design Decisions by number | ☐ |
| Does NOT include human escalation triggers | ☐ |
| Does NOT teach the 9/10-step tool chain | ☐ |
| Contains only patterns, examples, templates | ☐ |
| Could be implemented badly and still "work" | ☐ |

**If any check fails → do not publish.**
