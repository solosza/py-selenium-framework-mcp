## Part 1: Knowledge Acquisition Layer

**Question:** How do we acquire domain expertise without hiring domain experts?

**Answer:** Three-tier knowledge acquisition with decreasing cost and increasing specificity.

### 1.1 The Three Tiers

```
TIER 1: PUBLIC DOCUMENTATION                    COST: Free
────────────────────────────────────────────────────────────
• Industry standards (ISO, regulatory frameworks)
• Published best practices
• Open-source checklists and SOPs
• Professional body guidelines
• Academic and trade publications

Coverage: ~80% of domain rules
Speed: Immediate
Dependency: None


TIER 2: EXPERT PARTNERSHIPS                     COST: Revenue Share
────────────────────────────────────────────────────────────
• Edge cases and exceptions
• Practitioner nuance
• Validation and credibility
• Domain-specific terminology
• Failure modes and escalation logic

Coverage: ~15% of domain rules
Speed: Partnership timeline
Dependency: Vertical-scoped rev share (no equity)


TIER 3: CUSTOMER CUSTOMIZATION                  COST: They Pay You
────────────────────────────────────────────────────────────
• Organization-specific rules
• Custom thresholds and tolerances
• Internal workflow integration
• Proprietary enforcement logic

Coverage: ~5% of domain rules
Speed: On-demand
Dependency: Paid tier
```

### 1.2 Knowledge Acquisition Flow

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   PUBLIC DOCS   │     │ EXPERT PARTNER  │     │    CUSTOMER     │
│                 │     │                 │     │                 │
│  • Standards    │     │  • Edge cases   │     │  • Their rules  │
│  • Regulations  │────▶│  • Validation   │────▶│  • Their gates  │
│  • Checklists   │     │  • Credibility  │     │  • Their flows  │
│                 │     │                 │     │                 │
│   FREE (80%)    │     │  REV SHARE (15%)│     │  PAID TIER (5%) │
└─────────────────┘     └─────────────────┘     └─────────────────┘
         │                       │                       │
         └───────────────────────┴───────────────────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │    ENCODED RULESET      │
                    │                         │
                    │  Skills + Quality Gates │
                    │  = Execution Engine     │
                    └─────────────────────────┘
```

### 1.3 The Insight

> **The rules are public. Enforcement is the product.**

Everyone knows the rules. No one enforces them during AI execution.

Isagawa's value is not knowledge. Isagawa's value is:
- **Encoding** - turning docs into executable rules
- **Enforcement** - quality gates that block bad output
- **Customization** - making it theirs (paid tier)

## Part 2: Expert Partnership Model

**Question:** How do we add domain depth without hiring or equity dilution?

**Answer:** Vertical-scoped revenue participation with non-technical domain experts.

### 2.1 What Partners Contribute

Partners contribute **expertise artifacts**, not software:

| Contribution | Description |
|--------------|-------------|
| Canonical workflows | "Gold standard" processes |
| Decision criteria | Tradeoffs and judgment calls |
| Validation checkpoints | Required checks and gates |
| Edge cases | Exceptions and failure modes |
| Domain terminology | Precise definitions |
| Ongoing validation | Light review as domain evolves |

### 2.2 What Isagawa Retains (Non-Negotiable)

| Asset | Ownership |
|-------|-----------|
| Execution engine architecture | Isagawa only |
| Enforcement logic and validation | Isagawa only |
| MCP tools and runtime | Isagawa only |
| Product roadmap | Isagawa only |
| Pricing, packaging, distribution | Isagawa only |
| Customer relationships and billing | Isagawa only |
| All derivative works | Isagawa only |

Partners **license expertise**. They never own technology.

### 2.3 Incentive Structure

| Principle | Implementation |
|-----------|----------------|
| Compensation tied to vertical only | No claim on company-wide revenue |
| No governance rights | Partners advise, never decide |
| No perpetual obligations | Scoped and time-bound |
| Scales with adoption | Aligned incentives |

**Detailed terms:** See `isagawa_domain_expansion_model.md`

## Part 3: Agent-First Organization

**Question:** How do we operate the company without a team?

**Answer:** Agents execute. Founder orchestrates. Humans are optional and scoped.

### 3.1 Organizational Structure

```
                           FOUNDER
                      (Orchestrator Only)
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   CORE GOVERNANCE      PRODUCT FACTORY      BUSINESS FACTORY
   (Never scales)       (Per-vertical)       (Asymmetric scale)
```

### 3.2 Core Governance Layer (Protected)

These agents define **truth**. There are very few by design.

| Agent | Purpose | Authority |
|-------|---------|-----------|
| **Architecture Guardian** | Protect the Isagawa architecture | Can block releases |
| **Enforcement Authority** | Own definition of correct execution | Maintains DDs, gates |
| **Brand/Thesis Custodian** | Prevent category dilution | Guards positioning |

**These agents protect the moat.**

### 3.3 Product Factory (Scales by Vertical)

| Agent | Purpose |
|-------|---------|
| **Domain Research Agent** | Determine if domain is enforceable |
| **Domain Modeling Agent** | Convert knowledge to execution graphs |
| **Skill Authoring Agent** | Produce workflow guidance |
| **Validation Toolsmith Agent** | Build enforcement layer (MCP tools, gates) |
| **Adversarial Breaker Agent** | Break engine before users do |
| **Release Packaging Agent** | Ship without friction |

### 3.4 Business Factory (Asymmetric Scale)

| Agent | Purpose |
|-------|---------|
| **Market Signal Agent** | Identify demand before committing |
| **Pricing & Packaging Agent** | Optimize monetization |
| **Content & Education Agent** | Establish authority |
| **Sales Motion Agent** | Route demand efficiently |
| **Support Triage Agent** | Prevent founder involvement |

**Detailed agent specs:** See `isagawa_agent_first_organization_operating_model.md`

### 3.5 Humans (If Introduced)

If humans are ever added:
- They plug into **one agent only**
- They never see the full system
- They receive **revenue share, not equity**
- They hold **zero architectural authority**

> Humans are contractors to agents — not collaborators to the founder.

### 8.1 How to Build a New Vertical (End-to-End)

**Prompt to AI:**
> "I want to build an execution engine for [VERTICAL]. Follow the Isagawa Operating System in `isagawa_operating_system.md`."

**AI should execute:**

```
STEP 1: KNOWLEDGE ACQUISITION
─────────────────────────────
□ Search for public documentation:
  - Industry standards (ISO, regulatory)
  - Professional body guidelines
  - Published best practices
  - Open-source checklists/SOPs
□ Output: List of sources + extracted rules

STEP 2: DOMAIN MODELING
─────────────────────────────
□ Convert rules to execution steps
□ Identify decision points
□ Map validation checkpoints
□ Define what MUST happen vs. SHOULD happen
□ Output: Step graph + enforcement boundaries

STEP 3: SKILL AUTHORING
─────────────────────────────
□ Create skill file: `.claude/skills/[vertical]/SKILL.md`
□ Create step references: `.claude/skills/[vertical]/references/step-XX.md`
□ Follow existing skill patterns in codebase
□ Output: Complete skill with steps

STEP 4: QUALITY GATE BUILDING
─────────────────────────────
□ Create MCP tools: `mcp_server/tools/[vertical]/`
□ Implement validation logic
□ Define pass/fail criteria
□ Add escalation triggers
□ Output: Working quality gates

STEP 5: ADVERSARIAL TESTING
─────────────────────────────
□ Attempt to bypass each gate
□ Test edge cases
□ Document loopholes found
□ Harden enforcement
□ Output: Test results + fixes

STEP 6: PACKAGING
─────────────────────────────
□ Create test suite
□ Document usage
□ Package for distribution
□ Output: Shippable vertical
```
